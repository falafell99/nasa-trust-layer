## 1. Видение продукта — пять предложений

[Вероятно] Основной пользователь — ответственный за медицину член экипажа в момент, когда носимый монитор уже подал тревогу и нужно быстро понять, какие данные доступны для её проверки.  
[Догадка] За первые десять секунд он увидит исходный тип тревоги и её время, пригодность измерения и короткую причину, почему проверка поддерживает событие или оставляет его открытым.  
[Догадка] Он сможет открыть синхронные фрагменты ЭКГ и PPG и сверить их с причиной на карточке, действуя по действующему протоколу экипажа.  
[Вероятно] Потеря канала должна приводить к видимому состоянию «Событие не исключено», при этом исходная тревога остаётся на месте.  
[Вероятно] Жюри увидит работающий прототип, если одна и та же локальная программа воспроизведёт сигнал, обработает тревогу на отметке записи и покажет, какое наблюдение изменило вывод, а рядом команда предъявит результат на отложенных записях.

## 3. Три изменения с наибольшей отдачей

1. [Вероятно] **Сделать вывод проверяемым с экрана.** Постоянно показывать исходную тревогу, отдельную строку качества и отдельную строку вывода о событии. По клику на причину переносить курсор на конкретный участок. Формулировка «Событие не исключено» при плохом сигнале использует текущий статус «Проверь».
2. [Вероятно] **Зафиксировать, что считается выигрышем.** Главная таблица — сохранённые истинные, отклонённые ложные, неопределённые и истинные, ошибочно помеченные серым, с числителями и собственными знаменателями. Показать baseline «все тревоги сохраняются» и V0. Сравнение с V3 на тех же записях, если V3 готов. При нулевом выигрыше показать его и оставить опыт replay как демонстрацию поведения.
3. [Вероятно] **Добавить один режим повторения.** Один и тот же путь обработки для демо, измерений и пакетной оценки; в локальном журнале фиксировать ID записи, время тревоги, доступные каналы, статус и причину. Одной карточки достаточно, чтобы показать, откуда взялся вывод и какие данные были на тот момент.

## 4. Техническая архитектура

[Догадка] Один процесс Python 3.11 с WFDB, NumPy, SciPy и scikit-learn. FastAPI + Uvicorn на localhost отдаёт статическую страницу с Canvas и поток обновлений через SSE. Для управления replay хватит HTTP-команд start/pause/reset. Внешние ресурсы браузера, облако, LLM, CNN, Redis, брокер сообщений и переобучение на сцене в эту версию не входят.

[Догадка] Replay читает WFDB локально, отправляет пакеты по 250 мс с временем начала пакета и каналом по контракту `{t, channel, samples}`, а планировщик использует монотонные часы. Тревога CinC — отдельное событие источника на 5:00. Воспроизведение ускоряется сменой темпа выдачи, сохраняя время записи и порядок пакетов. Буфер сохраняет 5 мин по текущему дизайну, качество обновляется по последним 8 с раз в секунду, а верификация получает до 30 с до тревоги, включая последние 10 с отдельным окном признаков. При нехватке истории — «Данных недостаточно». Смена записи сбрасывает буфер и состояние пиков.

[Точно] CinC уже на 250 Гц и часть записей содержит отсчёты после тревоги. [Догадка] Читаем только первые 300 с до любой обработки; после 5:00 поток для этого прогона завершается. [Точно] Для BUT разметка задаёт границы в исходных отсчётах. [Догадка] Сопоставляем их по времени и ресемплируем сигналы антиалиасинговым `resample_poly` только доступный префикс окна, используя левый запас отсчётов для границы фильтра. История, показанная в браузере на момент t, строится только из доставленных к t данных. При проверке отсутствующие или некорректные значения помечаем явно, ABP в PPG не преобразуем, метки из заголовков и файлов разметки доступны только оценке. [CinC 2015](https://physionet.org/content/challenge-2015/1.0.0/) · [BUT QDB](https://physionet.org/content/butqdb/1.0.0/)

[Догадка] Ниже 22 предложенных скалярных признака. ECG1 — основное отведение по заранее закреплённому правилу чтения, ECG2 — второе; детектор пиков и нормализация одинаковы в оценке и replay. Неопределимые признаки остаются пропусками. Тип исходной тревоги — отдельная категориальная переменная источника.

|---|---|

ЧСС ECG2 по медиане RR. 7. MAD интервалов RR ECG2. 8. Доля пиков ECG1 с парой ECG2 при сопоставлении один к одному в допуске ±80 мс. |

[Догадка] **Модели и пороги.** V0 — фиксированное правило ECG-only. Затем одна логистическая регрессия с регуляризацией и признаками по каналам. Масштабирование и заполнение пропусков обучаются только на train, а индикаторы пропусков передаются модели. Шлюз начинает с правил на ЭКГ, показывающих качество входа как балл; перенос из BUT в ICU проверяется отдельно. Для порогов на validation сначала ограничить число истинных серых, затем максимизировать число ложных серых; если уровень не удаётся обосновать на валидационной выборке, отключить серый исход и показать получившееся покрытие. Плохой сигнал, отсутствие необходимого канала и промежуточный модельный балл ведут к «Проверь». Нужные для демонстрации пороги и правила заморозить до открытия hold-out. Процент модели публиковать как вероятность только после отдельной проверки калибровки; в UI достаточно статуса и причины.

[Вероятно] **Проверка.** CinC делить по записи с оговоркой о возможном пересечении пациентов; BUT — по субъекту, Q0 исключить из оценки качества и назвать долю исключённых отдельно. Сравнить тип тревоги, «сохранять всё», V0 и итоговый вариант на одинаковом hold-out. Жёлтые учитывать в общем знаменателе и как сохранённые для бинарной таблицы; при сравнении на подмножестве записей с PPG назвать размер и повторить baseline на нём. Для метрик результата — 95% интервалы бутстрапом по записи/субъекту и явное число истинных серых; при нуле таких ошибок добавить одностороннюю верхнюю границу с оговоркой о независимости. При слишком малом числе независимых субъектов назвать нестабильность интервала. [Протокол оценки](../05-evaluation-protocol.md)

[Догадка] **Runtime.** На одном фиксированном manifest замерить `perf_counter_ns` от последнего требуемого пакета до решения и отдельно от получения сообщения до отрисовки в браузере через локальные метки времени. Для полного времени пакет→UI связать события по ID и мерить на сервере до подтверждения отрисовки браузером, указав, что это верхняя оценка с обратной доставкой. Дать p50/p95, число событий, темп replay, модель ноутбука и режим cold/warm. Пик RSS процесса измерять средствами ОС или `psutil` и явно указать период опроса; размер артефакта модели — в байтах. Указать дату, хэш, команду и manifest. Нагрузку браузера считать отдельно, если её замеряли.

[Догадка] **Офлайн-запуск.** На второй ноутбук перенести код, manifest с контрольными суммами, локальный набор разрешённых файлов, замороженные параметры и wheelhouse под его ОС/архитектуру. При установленном Python одна команда `./run-demo.sh` создаёт venv, ставит закреплённые зависимости из wheelhouse с `--no-index`, проверяет файлы и поднимает localhost. Прогнать запуск на втором ноутбуке с отключённой сетью. Данные держать локально вне коммитов и соблюдать условия издателя. Это предложение по упаковке.

## 5. Экран

[Догадка] Верхняя полоса — «REPLAY», идентификатор источника и время записи. Постоянная карточка — «Исходная тревога монитора», тип и время. Под ней две строки: «Качество измерения» по каналам и «Проверка события» с текстовым статусом, причинами и видимыми пропусками. В центре — две дорожки ЭКГ и PPG с общей временной осью, вертикальным маркером тревоги и выделенным участком доказательства. В сцене BUT место PPG занимает ACC с подписью «движение», карточка тревоги показывает «источник без тревоги». Детали порогов, внутренние признаки, режим воспроизведения и системные логи доступны по раскрытию; экспертная метка скрыта до отдельного действия «Показать разметку».

[Вероятно] Главный элемент доверия — **строка причины, привязанная к участку сигнала**. Пример текста для случая с отсутствующим каналом: «PPG отсутствует. По ЭКГ событие не исключено». Статус читается без цветовой кодировки, исходная тревога остаётся видимой после выбора причины.
